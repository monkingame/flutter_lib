# Bug & Pitfall 知识库

维护项目的结构化 bug/坑点清单。每次踩坑或解决问题后调用本 skill 更新知识库，自动查重并在复发时标记次数。

## 调用时机

在对话中遇到 bug、踩坑、报错并解决后，调用 `/pitfall`。自动判断是初始化还是更新。

## 入口：状态判定（必读）

调用 `/pitfall` 后，按以下决策树走：

```
docs/bugs-and-pitfalls.md 存在？
  ├─ 否 → 项目根目录有主文档（CLAUDE.md / README.md 等）？
  │         ├─ 否 → 【场景 A】退出，让用户先 /init
  │         └─ 是 → 【场景 C】初始化（含子仓库检测）
  │
  └─ 是 → 文件是否为空/损坏（0 字节或无有效条目）？
            ├─ 是 → 同【场景 C】重新初始化
            └─ 否 → 用户是否明确要求"重新拆解主文档"？
                      ├─ 是 → 【场景 D】重新提取 + 合并（不覆盖已有条目）
                      └─ 否 → 【场景 E】正常更新模式
```

**关键约束（贯穿所有场景）**：不凭空编造，不翻旧账。对话中没有出现 bug/坑 就不记录。

---

## 场景 A：无主文档

**条件**：`docs/bugs-and-pitfalls.md` 不存在，且项目根目录找不到主文档

**操作**：
回复"项目尚未初始化（没有 CLAUDE.md 或 README.md），请先运行 `/init` 创建项目文档。"然后退出。

---

## 场景 B：有主文档，无坑章节

**条件**：`docs/bugs-and-pitfalls.md` 不存在，主文档存在，但主文档中没有匹配的坑章节

**操作**：
1. 回复"主文档中未找到集中的坑点章节。已创建空的 `docs/bugs-and-pitfalls.md`，后续遇到坑时调用 `/pitfall` 即可记录。"
2. 创建 `docs/bugs-and-pitfalls.md`，仅包含标题和简介（无条目）
3. 在主文档末尾追加"已知坑和注意事项"章节，指向 `docs/bugs-and-pitfalls.md`（格式同 C7 模板，去掉"高频重灾区"行——暂无条目）
4. 回到更新流程，检查当前对话是否有坑要记

---

## 场景 C：初始化（首次提取）

**条件**：`docs/bugs-and-pitfalls.md` 不存在（或为空/损坏），主文档存在

> 场景 C 的核心原则：**每个 git 仓库维护自己的 pitfall 文件**。git submodule 是独立仓库，应分别初始化；普通子目录属于本项目，统一管理。

### 步骤 C1: 发现主文档

按优先级在项目根目录查找：`CLAUDE.md` → `README.md` → 根目录下最大的 `.md`

### 步骤 C2: 检测 git submodule

运行 `git submodule status` 获取子仓库列表。如果项目根目录存在 `.gitmodules` 文件，其中列出的每个子模块都是一个独立 git 仓库。

**区分标准**：
- **git submodule**（`.gitmodules` 中有记录，或在 `git submodule status` 中列出）→ 独立仓库，分别初始化
- **普通子目录**（无独立 git 历史，只是项目内的文件夹）→ 本项目的一部分，坑统一记录

### 步骤 C3: 分别初始化每个子仓库

对每个 git submodule，以子仓库根目录为项目根，递归执行场景 C 的完整流程（C1→C2→C4→C5→C6）：

1. 在子仓库目录下查找主文档（`CLAUDE.md` → `README.md` → 最大 `.md`）
2. 扫描坑章节
3. 提取坑条目
4. 写入 `<submodule>/docs/bugs-and-pitfalls.md`
5. 精简子仓库自身的主文档

**子仓库之间互不可见**——每个子仓库只记录自己代码中的坑。这正是设计意图：当开发者单独 clone 某个子仓库并运行 `/pitfall` 时，它应该是完整的。

### 步骤 C4: 发现本仓库坑章节（同子仓库逻辑）

在**本仓库**的主文档中扫描全文所有 `###` / `####` 标题，逐一匹配以下模式：

`陷阱`、`踩坑`、`避坑`、`已知坑`、`坑点`、`已知问题`、`注意事项.*坑`、`Pitfalls`、`Known Issues`、`Bugs`、`常见问题`、`排查`

`排查` 仅当章节内容含坑点特征词（症状/根因/报错/exit code/崩溃/冲突/失败）时才算匹配，避免误匹配纯运维步骤。

**注意**：不限于某个父章节下，同一文档中不同父章节下的坑点都须提取。

### 步骤 C5: 提取本仓库坑条目

对每个匹配到的坑章节，解析其下的 `- ` 列表项和正文段落。

**排除**（保留在主文档，不迁移）：
- 含下载 URL + 版本号的表格
- 镜像链 / registry 地址列表
- API 端点文档引用
- "请将 XXX 放入" 类部署指令
- 纯配置参考

判别依据：不含"症状 / 根因 / 解决 / 报错 / exit code / 崩溃"等坑点特征词的条目 → 保留。

**如果本仓库的坑章节内容只是指向子仓库**（如"详见 `<子仓库>/docs/bugs-and-pitfalls.md`"），则只记录一条索引条目，不重复提取子仓库的内容。格式：

```
### 子仓库坑点索引
- **症状**: 本仓库为 monorepo 壳，实际代码在子仓库中
- **根因**: —
- **解法**: 各子仓库独立维护自身 pitfall 文件
- **关联文件**: <submodule-a>/docs/bugs-and-pitfalls.md, <submodule-b>/docs/bugs-and-pitfalls.md
- **发生**: YYYY-MM-DD (1 次)
```

### 步骤 C6: 写入本仓库 pitfall 文件

```markdown
# Bug & 坑点记录

> 由 `/pitfall` skill 维护。遇到新坑或复发时调用 `/pitfall` 自动更新。
> 条目格式：症状 → 根因 → 解法 → 关联文件 → 发生次数和日期。

---

## <模块名>

### <坑标题>
- **症状**: ...
- **根因**: ...
- **解法**: ...
- **关联文件**: path/to/file（无则 `—`）
- **发生**: YYYY-MM-DD (1 次)

---

## <下一个模块>
```

- 条目间 `---` 分隔
- `###` 标题用于后续查重
- 发生次数初始为 1

### 步骤 C7: 确保主文档有指针

**情况 A：C4 找到了坑章节** — 将原坑章节替换为索引。参考信息（下载地址/镜像链/API 引用等）留在原位置不动。

**情况 B：C4 未找到任何坑章节**（常见于新建子仓库） — 在主文档末尾追加"已知坑和注意事项"章节。此时去掉"高频重灾区"行（暂无条目），只保留指向 `docs/bugs-and-pitfalls.md` 的链接。

```markdown
## 已知坑和注意事项

> 详细记录见 [docs/bugs-and-pitfalls.md](docs/bugs-and-pitfalls.md)。
> 遇到新坑或复发时调用 `/pitfall` 更新。
>
> 高频重灾区：<按条目数排序的 top-3 模块，无条目时省略此行>
```

### 步骤 C8: 汇总报告

初始化完成后，报告整体结果：

```
本仓库：已迁移 N 条坑点 → docs/bugs-and-pitfalls.md
子仓库 <name>/：已迁移 M 条坑点 → <name>/docs/bugs-and-pitfalls.md
（每个子仓库各一行，数量按实际输出）
```

### 步骤 C9: 桥接到更新流程

检查当前对话上下文是否有刚解决但尚未收录的坑。有则进入场景 E 的查重+新增流程。

---

## 场景 D：重新拆解（用户明确要求）

**条件**：已有 `docs/bugs-and-pitfalls.md`，用户明确说"重新拆解主文档"或"重新初始化"

**操作**：
1. 读主文档，按场景 C 的方式重新提取
2. 与已有 `docs/bugs-and-pitfalls.md` **合并**：新提取到的条目与已有条目做查重，已有则不覆盖（保留已有条目的发生次数和历史日期），新增的追加
3. 告知合并结果（新增 N 条，已有 M 条保持不变）
4. 不触动主文档（已经精简过了）

---

## 场景 E：日常更新（最常用）

**条件**：已有 `docs/bugs-and-pitfalls.md` 且有效，用户未要求重新拆解

### 步骤 E1: 判断是否有坑要记

**铁律：不凭空编造，不翻旧账。**

```
用户带了明确描述（/pitfall xxx）？
  ├─ 是 → 有坑要记，继续
  └─ 否 → 扫描当前对话最近几轮消息
            ├─ 有 bug/坑 讨论或解决 → 继续
            └─ 没有 → 回复状态摘要并退出
```

状态摘要格式："当前共 N 条坑点，最近更新 YYYY-MM-DD。高频：xxx, xxx"

### 步骤 E2: 读取当前清单

读 `docs/bugs-and-pitfalls.md` 全文。

### 步骤 E3: 提取问题

从用户描述 + 对话上下文中提取：
- **症状**: 报错信息、异常行为、exit code 等
- **根因**: 定位到的根本原因
- **解法**: 最终采用的修复方案
- **关联文件**: 修改了哪些文件

缺的字段标 `【待补充】`。

### 步骤 E4: 查重

在已有 `###` 标题和症状中做关键词模糊匹配：
- 同模块 + 症状关键词重合 → 复发
- 不同模块但根因相同 → 同一问题，在原条目中追加
- 无匹配 → 新坑

### 步骤 E5: 更新或新增

**复发**：
- `**发生**` 行追加新日期，次数 +1
- 同一日期不重复追加（防止同一会话内重复调用多次）
- 若新解法比旧的更优，覆写解法
- 回复"已更新：`<标题>`，第 N 次"

**新坑**：
- 归入最匹配的已有模块（不创建过多细碎模块）
- 完全不同则新建 `## <新模块>`
- 按以下格式写入：

```markdown
## <模块名>

### <坑标题>
- **症状**: ...
- **根因**: ...
- **解法**: ...
- **关联文件**: path/to/file（无则 `—`）
- **发生**: YYYY-MM-DD (1 次)

---
```
- 回复"已新增：`<标题>` → `## <模块>`"

### 步骤 E6: 同步主文档索引

检查主文档的"高频重灾区"行是否仍准确。若不准确（top-3 变了）则更新。

---

## 普适约定（拷贝到其他项目时）

- 不硬编码项目名、文件名、路径
- 坑清单路径约定：`<项目根目录>/docs/bugs-and-pitfalls.md`（项目 CLAUDE.md 可指定其他路径；坑点很多时可按主题拆分为目录形态 `docs/bugs-and-pitfalls/`，含 README 分类表 + 主题文件，以项目约定为准）
- 主文档按优先级自动发现（`CLAUDE.md` → `README.md` → 根目录最大 `.md`）
- 模块名从文档自身标题推导，不预设
- 所有文件操作限制在项目目录内
- **绝不凭空编造**：对话无坑就不写
- **初始化后不重复分析主文档**：除非用户明确要求
- **无主文档不越权**：让用户先 `/init`，不替代 init 的职责
- **git submodule 各自独立**：每个子仓库维护自己的 `docs/bugs-and-pitfalls.md`；父仓库不汇总子仓库的坑（只记录索引指针）。普通子目录不属于子仓库，坑统一归入父仓库
- **当前仓库边界**：`/pitfall` 只操作当前工作目录所在的 git 仓库。在子仓库目录下运行 `/pitfall` 时，只管理该子仓库的 pitfall 文件，不感知父仓库
