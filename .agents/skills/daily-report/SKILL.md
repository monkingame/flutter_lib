# 工作日报生成

根据当天 git 提交记录和当前会话工作内容，生成简短日报。

## 模式

- **不带参数** → 标准日报，写入 `docs/worklog/<YYYY-MM>.md`
- **`-wechat`** → 微信版日报，只输出文字稿（不写文件），用于给领导汇报

---

## 微信版日报（`-wechat` 模式）

### 目标读者

领导，懂技术但不清楚细节。汇报成绩，不是流水账。

### 写作原则

- **以成绩为主**：做了什么、交付了什么、覆盖了多少
- **问题只写"已解决"的**：问题本身不是汇报内容，解决问题才是——写问题是为了衬托成果
- **不写下一步**：微信版只汇报已完成的工作，不规划未来
- **不写项目名和日期**
- **有数据就用数据**：几台、几次、几份文档，数字比形容词有说服力
- **2-3 段即可**，每段 1-2 句，越短越好
- **不提"今天""本周"**——领导看到时可能已经过了几天

### 参考风格 ⚡

```
1、<交付物> 已完成部署（<关键方式/环境>），累计 <N> 次压测验证。<达标结论与限制说明各一句>。
2、协助 <合作方> 验证 <事项>，正在尝试 <方法> 接入。
```

写作要点：
- **编号分条**：1、2、...，每条 1-2 句
- **数据具体**：约数可以，"400 多次"比"454 次"自然
- **动词精准不夸大**："协助验证"不是"完成"、"正在尝试"不是"接入成功"
- **关键背景不丢**：如"官方不建议"
- **不写"发现问题并修复"**——除非修复后彻底解决了，否则只说"仍在调试"

### ⚠️ 人类阅读 vs 机器阅读（务必牢记）

**人的阅读方式**：扫关键词，不是逐字解析。看到"完成""通过""已打通"→ 大脑自动补全为"全部搞定"→ 立即问"可以看看吗？"。人对否定词（"不要""还没""未完成"）敏感度极低——"不要摸烙铁"→人看到的是"摸烙铁"。

**机器阅读方式**：逐字节精确解析，能区分"完成了3/5"和"全完成"。

**因此，未完成的工作绝不能用完成类关键词**。以下词汇在未全部做完时禁用：

| 禁用词 | 替换为 |
|--------|--------|
| ✅ 完成、已通过、已打通 | 进行中、初步验证、正在测试 |
| ✅ 接入成功、部署完成 | 已接入（还需验证）、部署第一步完成 |
| ✅ 全链路打通 | 链路初步跑通，待完善 |
| ✅ 稳定运行、验证通过 | 当前轮次通过，继续压测 |

**原则：让领导看完不会以为这事已经完了。宁可让他觉得还在推进中，也不能让他误以为收工了。**

### 生成步骤

1. 收集信息：同标准日报步骤 1-2（git 提交 + 会话内容）
2. 提炼成绩：从当天工作中提取核心交付物和数字
3. 直接输出文字，不写文件

## 标准日报（不带参数）

### 1. 确定日期

取当天日期，格式 YYYY-MM-DD。如果用户指定了日期，以用户指定的为准。

### 2. 收集信息

两条路径，并行收集：

**(a) Git 提交记录**

获取当前作者名（或按项目 CLAUDE.md 声明的作者口径）：

```bash
git config user.name
```

对当前工作目录所在的 git 仓库执行：

```bash
git log --format="%h %ai %s" --since="<前一天日期> 00:00:00 +0800" --author="<上面获取的作者名>"
```

> **为什么用"前一天"而不是"当天"**：`--since` 的日期解析存在不确定性，一旦解析偏差可能静默漏掉部分提交（返回结果里每条都带日期，漏了不易察觉）。用前一天做起点多拉 24 小时数据（一个开发者一天最多几十条提交，数据量很小），拿到输出后按 `%ai` 字段精确过滤当天日期即可——**宁可多拉再过滤，不要少拉留盲区**。

> **为什么用 `--format="%h %ai %s"`**：`%ai` 输出固定格式 `YYYY-MM-DD HH:MM:SS +TZ`，每行自带日期，可逐行精确过滤；展示时可去掉日期转为 `--oneline` 风格（只保留 `%h %s`）。

要点：
- 过滤时只看每行 `%ai` 字段的日期前缀是否等于 `<当天日期>`，**精确过滤由模型自己完成**，不依赖 git 的 `--since`
- `--author` 做子串匹配，可覆盖同一用户的多台机器身份；也可用邮箱精确匹配
- 若项目存在学习/临时分支，建议限定主分支扫描（如 `git log main`），避免混入分支内提交

**Monorepo 项目**：若项目包含多个 git 仓库（submodule 或独立 git 目录），按项目 CLAUDE.md 声明的仓库清单**并行执行**上述命令（一次消息中发多个调用，减少等待），合并输出后统一按 `%ai` 精确过滤；根仓库也要检查（子模块指针更新也是当天工作的一部分）。未声明时默认仅处理当前目录所在的 git 仓库。

如果当天无提交，标注为"无提交"即可，不用强行编造。

**(b) 会话工作内容**

回顾当前 session 完成的主要工作（做了什么、解决了什么问题）。

### 3. 生成日报

将以上信息整合为简短日报。

**重要**：日报是给领导/非技术读者看的。必须把 commit 信息中的技术术语翻译成大白话。参考对照：

| 技术术语 | 大白话 |
|---------|--------|
| VO / BO / Entity / DTO | 数据字段/数据模型 |
| Service / Controller / Mapper | （直接省略，领导只关心功能不关心分层） |
| ossIds / ossId | 图片 |
| linkTitle / linkId | 关联标题/关联目标 |
| 新增 XXX 字段 | 增加 XXX 信息 |
| @Operation 注解 | API 文档注释 |

参考风格：

> 活动管理：
> 新增草稿状态，活动创建后默认为草稿需手动发布才可见；
> 新增终止活动功能，管理员可填写终止原因将活动状态变更为已取消；
> 完善所有接口的API文档注释，前端同事可直接查看参数说明。
>
> 通知公告：
> 新增小程序端获取公告详情接口。

格式规范：
- **模块标题独占一行**（如 `活动管理：`），冒号使用中文全角
- 该模块下的每个独立工作点**各占一行，行尾带分号**
- 不同模块之间**空一行**分隔
- 不写项目名和日期（日报文件本身已标注）
- 不写"明天继续""明天推进"等假设第二天的表述，需要时用"下一步"
- 这样 git diff 时每个工作点独立一行，便于对比变更

要求：
- 简短，每个工作点一句话
- 只写做了什么，不写技术实现细节（不出现类名、方法名、注解名等）

> 结构可按项目偏好调整：如项目习惯三段式（今天做了什么 / 遇到的问题 / 下一步），以项目 CLAUDE.md 约定为准。

### 4. 写入文件

**⚠️ 此文件为追加记录，永远不许覆盖已有内容。**

写入前必须先用 `Read` 工具读取文件当前内容。

默认写入路径：`docs/worklog/<YYYY-MM>.md`。如果项目 CLAUDE.md 指定了其他路径约定，以项目配置为准。

检查文件是否存在：
- 不存在 → 创建文件，写入 `# 工作日报 — YYYY年M月\n\n---\n\n## <当天日期>\n<内容>\n`
- 存在但当天日期已有 → 替换**仅当天日期**的那一小节（不是整个文件）
- 存在且当天日期没有 → 在文件末尾追加 `\n## <当天日期>\n<内容>\n`

写入时优先用 `Edit` 工具的 `old_string` + `new_string` 精确追加，或 `>>` 追加重定向。**严禁用 `>` 覆盖写入。** 若 `Edit` 因中文长文本匹配失败，可改用 Python 脚本按 `## <当天日期>` 标记定位小节后替换/追加（保留旧内容，避免整文件重写）。

**写入后必须验证**：用 `Read` 工具读回文件末尾，确认：
1. 当天日期只出现一次（没有重复的 `## <当天日期>`）
2. 内容完整无截断
3. 之前的条目没有被破坏

### 5. 输出

展示生成的日报内容给用户确认。
