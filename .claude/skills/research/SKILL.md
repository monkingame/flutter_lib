# 通用调研 Skill

给定关键词或提示词，进行多源调研，结果存档到 `research/`。

## 触发

- `/research <关键词/提示词>` — 调研指定主题，新建文档
- `/research -redo <文档路径>` — 基于已有调研文档重新调查，核实最新内容，原位更新
- 用户说"调研一下 XX""调查 XX""搜一下 XX 的对比"

## 可配置项（CLAUDE.md）

项目可在 `CLAUDE.md` 中声明以下配置来覆盖默认行为：

```markdown
## 调研配置

- research.output: 调研报告输出目录，默认 `research/`
- research.skip-dirs: 项目内搜索时跳过的目录（glob），默认 `.git/`, `node_modules/`
```

未声明时使用默认值。

## 🛑 禁止跳步（铁律，2026-09-20 修订）

以下环节**不可因"信息已够/主题简单/官方单页已覆盖"而跳过**；确需跳过时必须：① 在报告头部 `⚠️ 未完成项` 显式列出 ② 告知用户。判断依据不是主观感受，而是步骤 5 输出前的「完成检查（DoD）」逐项打勾：

1. **步骤 4 之 Playwright**：时效信息（版本/日期/价格/状态/API 变更）必须用 Playwright 打开源页面确认；WebFetch 只作辅助通道，**不得替代** Playwright
2. **步骤 4.5 web-survey + 回帖核实**：命中关键网站判定（官方文档/代码仓库/论坛/实时数据）即必须调用 web-survey；无社区回帖来源时写"未找到"，**不得省略该环节**
3. **多源交叉验证**：关键数据 ≥2 独立来源；唯一来源必须在报告中标注"单源，未交叉验证"

## 入口

```
/research <主题>              → 新建调研：步骤 1 → 2 → 3 → 4 → 4.5(web-survey) → 5 → 6 → 7
/research -redo <路径>        → 重做调研：步骤 R1 → (复用 2~5) → R2 → R3
```

### 新建调研

正常流程，见下方步骤 1~7。

### 重做调研（-redo）

基于已有调研文档重新调查，**不抛弃原有内容**——在原文档基础上核实、更新、补充最新信息。

**步骤 R1：读取现有文档**

1. 读取指定的调研文档（如 `research/xxx.md`）
2. 从文档头部提取：
   - 调研标题
   - 原始调研日期
   - 使用过的关键词（`🔗 关键词` 行）
   - 原始结论
3. 确认重做范围：全量重查 / 仅核实特定部分（可追问用户）

**步骤 R2：重新调研**

- 使用原有关键词 + 新增"2026 最新""latest"等时效性关键词
- 完整执行步骤 2~5（项目内搜索 → Web 搜索 → 深度获取 → 4.5 关键网站 web-survey → 整理输出）
- **重点**：版本号、日期、状态变化、API 变更等时效性数据必须用 Playwright 直接打开源页面确认（见步骤 4 最新优先原则）；关键网站同样走步骤 4.5 用 web-survey 抓最新状态，而非仅重搜

**步骤 R3：原位更新文档**

在**原文档末尾**追加，不覆盖原有内容：

```markdown
---

## 🔄 重新调研 — YYYY-MM-DD

> 📅 距上次调研：N 天
> 🔍 方法：<用到的搜索方式>
> 🔗 新增关键词：<本次新增的关键词>

### 变化摘要

（列出与上次调研结论的差异：哪些变了、哪些没变、哪些新增）

### 更新详情

（结构化内容——格式同首次调研）

### 当前结论

（综合新旧调研的最新结论）
```

**更新文档头部**：将调研日期更新为本次日期，追加 `🔄 YYYY-MM-DD` 标记。

## 步骤

### 1. 解析输入

从用户输入中提取调研主题。如果主题太宽泛，先追问 1-2 个收敛问题再动手。

### 2. 项目内搜索

先用 Grep + Glob 在仓库内搜索相关资料——可能有之前的调研、文档、参考手册已经覆盖了部分内容。搜索范围覆盖全仓库（排除 `.git/`、`node_modules/` 等非文档目录），重点搜索：

- 已有的调研报告（`research/` 或类似目录）
- 项目文档（`docs/`、`README.md`、`CLAUDE.md` 等）
- 项目内可能的部署/参考文档（如 `deploy/`、`docs/man/` 等）
- 相关的 skill 定义或参考手册（`.claude/skills/` 等）

已有资料可直接引用，避免重复调研。

### 3. 多源 Web 搜索

至少使用两条搜索路径（并行），优先使用当前环境可用的 Web 搜索工具：

- **通用 Web 搜索**（如 Brave Search MCP、Tavily Search MCP 等）— 覆盖中英文资料
- **深度调研**（如 Tavily Research MCP 等，可选）— 主题复杂时使用

每条路径搜索 2-3 组不同角度的关键词，覆盖完整。

> **通用化说明**：本 skill 不硬编码具体 MCP 工具名。各项目根据自身 MCP 配置选择可用的搜索工具。如项目未配置任何 Web 搜索 MCP，则跳过 Web 搜索步骤，仅做项目内搜索。

**关键网站标记**：搜索结果中出现「关键网站」（定义见步骤 4.5）时，标记为候选，不依赖搜索摘要下结论——摘要可能过时或失真，紧接着进入步骤 4.5 用 web-survey 深挖。

### 4. 深度获取（Playwright = 主通道，强制；WebFetch = 辅助）

**🛑 主通道规则（不可协商）**：凡时效性信息（版本号、发布日期、API 变更、价格、状态、配额等），**必须**通过 Playwright 打开源页面确认至少一次（`browser_navigate` → `browser_wait_for` → `browser_snapshot`）。"搜索结果已有一致摘要""WebFetch 已抓到全文"**均不构成豁免**——搜索索引可能延迟、WebFetch 可能拿到缓存/非渲染版本。

**通道层级**：

| 层级 | 方法 | 用途 | 约束 |
|------|------|------|------|
| 主（强制） | Playwright MCP | 源页面确认、动态页、需交互页、落地页验证 | 每个关键数据点 ≥1 次；`browser_navigate` → `browser_snapshot` |
| 辅（可选） | WebFetch | 并行拉取静态长文（博客/文档全文） | 仅作素材补充；**不得替代** Playwright 确认 |

**Playwright 使用流程**：

1. `browser_navigate` 打开目标 URL
2. `browser_wait_for` 等待关键内容加载（如 `text: "2026"` 或特定关键词）
3. `browser_snapshot` 获取页面结构化内容（比 `browser_take_screenshot` 更适合数据提取）
4. 如需翻页/切换 tab → `browser_click` 后再次 snapshot
5. 提取关键数据后 `browser_close`（或留待下一页）

> ⚠️ **最新优先原则**：Web 搜索索引可能有延迟。对于版本号、发布日期、API 变更、价格、状态（✅/❌）等时效性信息，**必须用 Playwright 直接打开源页面确认**，不依赖搜索摘要。搜索结果与页面实际内容矛盾时，以页面实际内容为准。
>
> ⚠️ **Playwright 不可用时**：环境未装浏览器/执行失败 → 不得静默降级为 WebFetch 交差。处理：① 报告头部 `⚠️ 未完成项` 列出"Playwright 未执行：<原因>" ② 步骤 7 告知用户 ③ 仅当用户明确允许降级时才以 WebFetch 为准并标注"未 Playwright 确认"。

### 4.5 关键网站深度调研（调用 web-survey skill）

**定位说明**：web-survey 是**网站全站遍历工具**（只读抓取站点结构与内容），research 才是**调查工具**——本步骤由 research 调用 web-survey 作为数据采集手段，web-survey 不做调研决策。

**「关键网站」判定**（满足其一即触发 4.5）：

1. **核心技术相关资料**：wiki、RFC、官方文档/规范、标准等
2. **核心代码仓库**：GitHub 等（repo、discussions、issues——回帖量大，只有全站遍历才能充分探索）
3. **本次调查点的主要介绍资料**：原理、架构、白皮书等
4. **通过搜索引擎搜索到的其他关键网站**：信息密度高 / 权威性高
5. **需要最新实时数据**：版本号、日期、状态、API 变更、价格等（与步骤 4「最新优先原则」联动）

**执行**（命中判定即强制执行，无"信息已够"豁免）：

- 项目已安装 `web-survey` skill → **必须**调用它全站只读遍历，产出 `docs/survey/<site>-survey-ref.md`
- 从手册中提取最新数据与回帖/社区内容，回填到调研报告，**标注来源与抓取日期**
- 项目**未安装** `web-survey` / 遍历失败 → **不得静默跳过**：在报告头部 `⚠️ 未完成项` 列出 + 步骤 7 告知用户
- **回帖核实为必做项**：至少打开/检索 ≥1 个讨论来源（GitHub issue/discussion、论坛帖、Reddit 帖等）；实际找到 → 走下方质量识别后入库；找不到 → 报告中显式写"社区回帖核实：未找到"，不得省略该行

**价值**：

- **实时性**：web-survey 直接打开最新页面抓取，不受搜索索引延迟影响，数据比搜索摘要新
- **回帖充分探索**：论坛/GitHub 讨论区的大量回复只有全站遍历才能看到，搜索摘要是覆盖不全的

#### 回帖/社区内容质量识别（防污染）

**🛑 铁律：非官方信息默认不可信**。任何来自论坛/GitHub issue 评论/Reddit/第三方博客/聚合站的性能数字、结论、对比，**一律视为未验证**——必须先做质量识别（下方流程）+ **≥2 个独立来源交叉验证**（或与官方文档/源码一致）后，才可写入报告「✅ 已验证结论」；未通过验证的只能进入「⚠️ 社区说法（未验证）」小节，**严禁**混入已验证结论。**禁止"看到什么就听信什么"**；宁可写"无可靠来源，未验证"，不得照抄。

社区回帖（论坛回复、issue 评论、discussion 讨论等）质量参差，可能含**错误、过时、水贴、广告、误导性**内容。**先识别、后入库**，严禁看到数据就抓，污染数据源：

- **权威分层**（按可信度从高到低）：
  - 官方回复：maintainer/官方账号/项目成员、置顶/采纳标记
  - 高赞且多来源印证的回帖
  - 普通用户回帖（仅作线索，不作结论）
  - 无依据、过时、广告/水贴（不入库）
- **识别信号**：
  - 发布时间——是否已过时（被后续版本/更新覆盖）
  - 账号身份与徽章——官方/贡献者/普通用户
  - 采纳/置顶/高赞标记
  - 与官方文档、源码是否一致
  - 是否被后续回帖修正（注意回帖时间线）
- **负面内容处理**：错误/误导/水贴/广告**不写入调研报告**；如必须提及，明确标注「社区说法，未验证，与官方文档矛盾」
- **交叉验证**：回帖结论须 ≥2 个独立来源（官方文档/源码/其他回帖）印证后才写入结论
- **分离记录**：调研报告中区分「✅ 已验证结论」与「⚠️ 社区说法（未验证）」

### 5. 整理输出

将多方信息整合为结构化报告：

- **结论优先**：先给结论，再给论据
- **对比用表格**：版本对比、产品对比一律表格
- **数据带引用**：关键数字标来源链接
- **标注适用性**：哪些对当前项目有用、哪些无关
- **边界自检**：输出前确认：① 无特定服务器引用（IP/编号） ② 无可执行命令（shell 代码块） ③ 只给是/否结论不设计操作流程 ④ 不做具体部署方案选型

**✅ 完成检查（DoD——逐项打勾，任一未过 = 报告状态"未完成"，补做后方可进入步骤 6）**：

- [ ] 至少 1 个关键源页面已用 Playwright 打开确认（记录 URL + 抓取日期）
- [ ] 关键网站（官方文档/代码仓库/论坛）已触发 web-survey 或最少做了回帖页检索
- [ ] 社区回帖已核实并做质量识别（或显式写"未找到"）；**入库的每条社区结论均已 ≥2 独立来源印证或已标注「社区说法（未验证）」**，无未经审核的社区数据混入已验证结论
- [ ] 关键数据 ≥2 独立来源；唯一来源已标注"单源，未交叉验证"
- [ ] 报告含「✅ 已验证结论」与「⚠️ 社区说法（未验证）」分离段落
- [ ] 无未完成项遗漏：若存在，报告头部 `⚠️ 未完成项` 已列出且步骤 7 已告知用户

### 6. 存档

写入 `research/<主题-slug>.md`，格式：

```markdown
# <调研标题>

> 📅 调研日期：YYYY-MM-DD
> 🎯 相关项目：<所属 skill/项目名>（如无特定归属写"通用"）
> 🔍 方法：<用到的搜索方式>
> 🔗 关键词：<搜索用过的关键词>
> 🔎 Playwright 核实：<URL × N（每项含抓取日期）；必填——无则写"未执行：<原因>">
> 💬 社区回帖核实：<结论 / 未找到；必填>
> ⚠️ 未完成项：<无 / 列出未执行项与原因；必填>

---

## 结论

（3-5 句话总结）

---

## 调研正文

（结构化内容；已核实结论与社区说法分节/分标注）
```

### 7. 告知用户

```
调研完成 → research/<文件名>.md
结论：<一句话>
完成检查：✅ 全过 | ⚠️ 未完成项（列明：Playwright 未执行/回帖未核实等原因）
```

## 原则

- **结论先行**：先给答案再给过程
- **最新优先**：时效性信息（版本/日期/价格/状态/API 变更）以页面实际内容为准，不依赖搜索摘要；**必须**用 Playwright 直接打开源页面确认（主通道，见步骤 4），WebFetch 不替代
- **实时优先**：关键数据以 web-survey 抓取的源页面为准（见步骤 4.5），并标注抓取日期
- **防污染**：社区回帖先做质量识别再入库（权威分层、交叉验证、时间线），错误/误导/水贴/广告不写入；未验证说法显式标注「社区说法」
- **多源交叉验证**：关键数据至少 2 个独立来源
- **必落盘**：不存档的调研 = 下次还得重做
- **标注归属**：每个文档标注触发项目，方便以后按项目回溯
- **去重优先**：项目内已有的资料不重复调研，引用即可
- **参考书而非操作手册**：调研文档是"最新的全面参考书"——提供事实数据、参数整理、已知问题、简单推论。**不越界为操作手册**。
- **职责边界**：
  - ✅ 官方推荐配置 + 常见规格简单外推（如"官方建议 4×H100，按此推算约需 4×A800"）
  - ✅ 是/否结论（某方案/某技术是否可行、是否支持，原理性判断）
  - ✅ 已知问题/风险罗列（如"某架构未官方验证""仅某代硬件支持"）
  - ❌ 针对特定服务器的部署方案设计（如"用某台机器的 GPU""选 A 机还是 B 机"）
  - ❌ 可执行的安装/启动命令（如 `vllm serve ...`、`docker pull ...`、模型下载命令等）
  - ❌ 多步骤操作流程和行动建议（如"先用 X 验证再上 Y""建议下一步…"）
  - ❌ 协议桥接的具体实现方案（如"写服务脚本做 JSON↔multipart 翻译"）
- **越界检查**：输出调研文档前自查——是否出现了特定服务器 IP/编号？是否有可执行的 shell 命令？是否在替部署决策选型？出现任一项即越界。
