# 阶段性存档

分析当前 git 仓库的变更，生成精准的中文提交说明，提交并推送。相当于游戏的存盘点——把当前进度固化下来，方便日后回溯。

本 skill 是**跨项目通用动态版**：提交说明的格式与语言风格读取**项目指令文件**（`AGENTS.md`，旧项目为 `CLAUDE.md`）中的提交规范声明，不硬编码前缀；项目未声明时使用默认格式。

## 参数

- `/checkpoint` — 展示摘要，等待确认，提交推送
- `/checkpoint -y` — 展示摘要，跳过确认，直接提交推送

**⚠️ /checkpoint 只做提交推送一件事。完成后立即停止，不延伸、不猜测、不处理上下文中的任何"待办"。**

## 步骤

### 1. 定位仓库

```bash
git rev-parse --show-toplevel   # 确认仓库根目录，避免在子目录下漏看变更
```

此仓库即为操作目标。

**Monorepo 项目**：若项目指令文件声明了子仓库路径列表，则对每个有变更的子仓库依次执行以下流程；默认仅处理当前目录所在的 git 仓库。

### 2. 检查变更

```bash
git status --short
```

如果没有未提交变更（包括 unstaged 和 staged），告知用户"没有需要提交的变更"并退出。

### 3. 读取 diff

执行 `git diff` 和 `git diff --cached` 读取完整改动内容。必须仔细读 diff，理解每个文件改了什么。

（`-y` 只跳过确认步骤，不降低本步骤要求——提交说明必须基于完整 diff。）

### 4. 确定提交格式

读取项目指令文件（`AGENTS.md` / `CLAUDE.md`）中的提交规范声明（查找"提交前缀""提交格式""提交规范"等关键词），确定格式：

- **有前缀声明**（如 `aio:`、`ai:`、`dsh:`、`学习:`）：`<前缀> <模块/主题>：<做了什么>`
- **无声明（默认）**：`<模块名>：<做了什么>`
- **文档库类项目**（声明 `<分类/章节>` 格式时）：新增章节 → `添加章节: <category>/<slug>`；修改已有 → `<category>/<slug>: <改动>`；skill/配置类 → `项目配置: <改动>`；杂项 → `其他: <改动>`

**条件：`learn/*` 分支**（仅当项目采用学习分支时）——学习分支的提交不进入日报，仅供自己回顾：格式用 `学习: <内容>`，可用技术术语，无需通俗化。

**条件：日报通俗语言**（仅当项目有 `/daily-report` 或声明日报引用时）——提交说明会被日报引用给领导看：用通俗语言，避免技术术语（如 VO、BO、Service、ossIds → 用"数据字段""数据模型""服务端"等替代）。

### 5. 生成提交说明

- 核心改动写清楚，不写过程细节
- 简短，2~3 句话
- **只描述本次 diff 中的改动**，不要包含之前已提交的内容
- 多个不相关的改动可分别列在 commit body 中

### 6. 展示摘要

```
提交说明：<说明内容>
变更文件：<文件1>, <文件2>, ...
```

### 7. 确认（仅无 -y 时）

如果没有传 `-y` 参数，询问用户确认。用户可要求修改提交说明。
如果传了 `-y`，跳过询问，直接进入第 8 步。

### 8. 提交并推送

```bash
git add <具体文件1> <具体文件2> ...
git commit -m "<提交说明>"
git push
```

- 用具体文件名而非 `git add .` 或 `git add -A`，避免误提交
- `git status --short` 中列出的修改文件（`M`/`A`）全部 add；未跟踪文件（`??`）默认不提交，除非用户明确要求
- 不要跳过 hooks（不用 `--no-verify`）
- 如果 push 失败（如需要先 pull），如实报告并提示用户处理，不强行

### 9. 收工

提交推送完成后只输出确认信息，**不做任何其他事**。
