# 手册生成（gen-man）

## 定位与原理（重要，先读）

- **gen-man 是一套完整的通用部署流程模板**，不是某个项目的专属说明书：
  - 输入任意项目的素材 → 产出「**版本快照 + 分步操作指引**」手册；
  - 核心保证：**同环境 + 照手册 = 复现一致的部署结果**——通过「固定当前使用版本（snapshot）」实现：手册固化部署时刻的确切版本与参数，消除版本/参数漂移；读者不需要自己去查版本、猜参数。
- **可移植**：本 skill 可**整体复制到其他项目/其他仓库**直接使用。它只含**通用流程与方法论**，**不硬编码任何项目专属事实**（模型名、版本号、机器编号、路径、数值、fork 名、端口等）——具体数字一律来自目标项目素材（ops-log/raw-log），缺失标「待实测」。
- **已实现实例验证**：本模板已在真实项目中落地，包括"官方不支持硬件 → 社区补丁"这类**非标准部署**场景。实例产物手册保存在各项目仓库的 `docs/man/`，不随本模板分发。
- 仓库路径约定（`docs/man/`、`deploy/NN-*`、`.claude/skills/`）按各项目仓库实际调整；本 skill 的输入只有「项目素材目录」。

---

## 调用格式

| 调用 | 行为 |
|------|------|
| `gen-man` | 显示使用说明 + `docs/man/README.md` 现有手册清单 |
| `gen-man <名称>` | 展示该名称已有手册（或提示缺少模式），**不生成** |
| `gen-man <名称> -deploy` | 生成/更新 **部署安装手册**（安装/运维人员用） |
| `gen-man <名称> -usage` | 生成/更新 **使用手册**（最终用户用） |

**铁律**：
- 参数不全（缺名称或缺模式）→ **只展示/提示，绝不生成**；
- 名称解析不唯一 → **列出候选让用户选，绝不猜测**；
- 目标手册已存在 → **先检测更新再问是否重生成**，无更新直接展示现有手册。

## 第一步 解析 `<名称>` → 项目目录

### 1.1 输入形态

`<名称>` 可以是项目名 / deploy 目录名 / skill 名，均自动归一化（小写、去 `.` `-` `_` 空格）后匹配。
示例：`myproj`、`02-myproj-v2` 均可。

### 1.2 解析顺序（命中即停，从上到下）

1. **索引命中**：`docs/man/man-<名称>-deploy.md` 或 `man-<名称>-usage.md` 已存在 → 该项目（以 `docs/man/README.md` 为索引记录）。
2. **目录基本名**：遍历 `deploy/NN-*`（忽略非项目目录，如 `logs`、`manual`、`scripts` 等，按项目实际约定），去掉 `NN-` 前缀与尾部状态词（如 `-abort`）得基本名：
   - 基本名 == 名称 → 唯一候选；
   - 基本名包含名称，或名称包含基本名 → 候选；
3. **关键词扫描**：把名称分词（如 `myproj-v2` → `myproj` `v2`），在仓库项目描述行与 `deploy/` 目录名中匹配。
4. **skill 名**：`.claude/skills/<名称>/SKILL.md` 存在，且其内容指向某个 `deploy/NN-*` 目录 → 该项目。

### 1.3 裁决

- **唯一** → 使用该目录；
- **多个** → 列出候选（目录 + 一句话说明），要求用户回复数字选择；
- **零** → 提示「未找到项目 `<名称>`」，展示 `deploy/NN-*` 全部可解析项目清单。

> ⚠️ **别名/映射不预填**：只有真正生成过手册的项目才出现在 `docs/man/README.md`。「用到谁生成谁」——不预先列一堆名字造成"看似已有"的误导。

## 第二步 存在与更新检查

目标文件：`docs/man/man-<名称>-<deploy|usage>.md`

- **不存在** → 直接进入 §第四步「生成」；
- **存在** → 更新检测：
  1. 读手册头部元数据行 `> 生成/更新：<时间戳> | 依据：<ops-log 最后条目日期>`；
  2. 对比项目 `ops-log.md` 最后条目日期与 `raw-logs/` 最新文件时间；
  3. **结构规范校验**：手册是否满足当前 skill 规范必需章节（如 deploy 的「版本/指纹快照表」）——缺失则视为需更新；
  4. **无更新** → 提示「手册已是最新（依据 YYYY-MM-DD）」，展示现有手册（Read 内容），**结束**；
  5. **有更新 / 结构缺失 / 用户明确要求重新生成** → 列出差异（如「ops-log 最后条目 从 08-22 → 09-05」或「缺版本/指纹快照表」），询问「是否重新生成？」——确认后更新，否则结束。

> 注意：手册统一以 `docs/man/` 为准；项目目录下历史散落手册不作为目标（仅可作素材参考）。

## 第三步 素材收集

读取 `<项目目录>/`（按存在与否取舍）：

| 文件 | 用途 |
|------|------|
| `plan.md` | 阶段划分、命令模板、坑点对照 |
| `ops-log.md` | 进度、决策、验收数据、版本/参数快照（**必读**） |
| `raw-logs/` | 原始输出、启动日志关键行、实测数字、验收原始记录 |
| `optimization.md` / `evidence-*.md` / `research-*.md` / `opencode-integration.md` | 深层背景、补丁来龙去脉（存在才读） |
| 坑点档案 `docs/bugs-and-pitfalls/*.md` 中相关条目 | 坑点来源（**deploy 手册置尾；usage 手册不涉及**） |
| 跨项目 `research/*.md`、`docs/man/README.md` | 背景调研与索引参照 |

> **验证用数据必须从素材提炼**：版本号、commit 指纹、md5、文件数、磁盘/加载大小、每卡显存、KV pool/并发、`system_fingerprint` 形态、启动日志关键值——全部来自 `ops-log.md`/`raw-logs/` 实测，**不凭空编造**（缺则标「待实测补充」）。deploy 手册的版本快照、usage 手册的时延/容量预期，都由这些数据支撑。

## 第四步 生成

### 真实性/脱敏规则（**按模式区分**，任何模式密码绝不出现）

生成后**自动执行校验扫描**，不可跳过。

**① 两模式共有（铁律）**
- **密码 / 密钥 / API Key 绝不写入任何手册**；收尾必须 grep `密码|password|pwd|sshpass|api[_-]?key` 0 命中（**SDK 接入示例中的 `api_key="not-needed"`/`"EMPTY"` 属占位，不算命中**——此类示例是必须保留的可复制代码）；
- 某操作确实需要凭据时，用 `<需向管理员申请>` 占位，并写明申请途径，不写任何实际值。

**② deploy 模式：完全脱敏（面向安装人员，手册可对外）**
- 内网 IP → `<目标主机IP>`；Ceph/RGW 等内部服务地址一律占位；
- 机器名/编号 → `<第一台部署机>`、`<第二台部署机>`（同部署多台按序编号）；
- 用户名保留 `root`，其余 → `<用户名>`；`/home/<用户名>/...` 路径归一；
- 命令保持**可复制可执行**（占位符替换后仍能跑；`localhost`、通用路径如 `/data/models/...` 保留）；
- 收尾 grep：内网 IP 段、机器名/编号模式、`/home/` 路径等敏感模式 0 命中（正则按项目实际 IP 段与命名约定确定）。

**③ usage 模式：真实连接信息（面向最终用户，必须能直接用）**
- **IP/域名/端口、用户名、模型名、API 端点、路径等 = 必须与实际部署完全一致**（取自 `ops-log.md` / `raw-logs/` / 已验证的 curl 输出），否则就不是真实的使用手册；
- 每个真实值须可**溯源**到素材（ops-log / raw-log / 验收数据）；
- **密码/密钥绝不出现**；认证类信息（API Key、登录密码）一律用 `<需向管理员申请>` + 申请方式代替；
- 收尾校验：提取的真实值（IP/用户名/端点）逐项与素材核对一致，无编造。

> 逻辑：deploy 手册讲"怎么装"，IP/用户是内部信息该脱敏；usage 手册讲"怎么用"，IP/用户就是连接凭据的一部分，不真实 = 不可用；两者共用底线——**密码绝不落盘**。

### 元数据头（落盘必写，更新检测依赖它）

```markdown
> 生成/更新：<YYYY-MM-DD HH:MM> | 依据：<项目 ops-log 最后条目日期>
```

### 版本固化（snapshot）——deploy 手册的核心

**原则**：把**部署时刻的确切版本/参数**固化为「快照表」，读者只要环境相同即可复现。**缺版本、缺关键参数、缺验证命令 = 手册不合格。**

**通用快照表字段**（应用到项目时填入真实值，每项必须配「验证命令」）：

| 类别 | 必填字段 | 通用验证命令 |
|------|----------|------------|
| 模型 | 仓库全名、版本（如日期标签 0731） | `ls` 模型目录、`import <pkg>`、官方更新日志 |
| 权重 | 文件数、磁盘大小、加载体积、每卡显存 | `ls \| wc -l`、`du -sh`、启动日志 |
| 推理框架 | **wheel 全名（含 commit 指纹）**、**基线版本 vs 上游最新 vs 硬件兼容性**、md5、关键依赖版本 | `__version__`、`md5sum`、`pip list \| grep <pkg>` |
| 服务指纹 | `system_fingerprint` 形态（含版本+TP 后缀）、API 模型名 | curl 响应、`/v1/models` |
| 性能 | KV pool tokens、并发倍数、max-model-len、时延 | 启动日志、压测记录 |
| 关键参数 | 并行/显存/KV dtype/上下文/模型名等启动参数 | 启动日志 `non-default args`、service/容器定义 |

> 数据来源只允许 ops-log/raw-log/实测，绝不编造；缺项标「待实测」。

### vLLM 通用要点（skill 内置方法论，数值由素材提供）

大多数大模型部署都会用到 vLLM，**版本处理是通用关键**。任何项目都按以下四步走：

1. **兼容性核对（部署流程第一步）**：模型的**官方支持硬件（SM 代次）** vs 实际部署硬件
   - 支持 → 用官方 vLLM（并注明适用版本）；
   - 不支持 → 找社区 fork/补丁；手册需记录：**fork 仓库、基线版本、补丁来由（issue → PR → commit）、如何安装**；
   - **上游最新版本**为时效性数据：以生成时 Web 检索（PyPI/GitHub Releases）为准，或引素材中的调研结论；素材缺失则标「待确认真实版本」。
2. **版本固化**：wheel 全名（含 commit 指纹）+ md5 + 依赖版本 → 见「版本固化（snapshot）」节；
3. **版本验证**：
   - `python -c "import <pkg>; print(<pkg>.__version__)"`（⚠️ **离开源码目录执行**，防源码树遮蔽 site-packages）；
   - 启动日志 banner / `system_fingerprint`（含版本 + TP 后缀）核对；
   - `pip list | grep <pkg>`、`md5sum <wheel>`；
4. **复现保证**：把上述核对结论写入手册（"为什么用这个版本/这条路"），并给出同环境重建所需的全部版本信息与命令。

### 标题与简称规范（两模式统一）

- 手册标题使用**完整名称**（如 `# <模型全名> 使用手册`），**不在标题括号里塞简称/缩写**（如 `（<简称>）`：语义有歧义，简称与别名无法区分）；
- 需要简称时，在**正文开头**（标题下方首段/引言块引用）声明：`<模型全名>（以下简称 <简称>）`，后续正文再用简称；
- 标题括号只允许限定**语境/方案**（如 `（8×L40S / <特殊方案>）`），不允许放简称或英文缩写；
- 首段建议同时给出：简称声明 + 模型版本（如日期标签）+ 一句话定位（如开源协议、与官网 API 同款权重）。

### 模式 A：部署安装手册（`-deploy`）

**目标读者**：安装/运维人员。**手册 = 版本快照 + 分步操作指引**——固化部署时刻的确切版本与参数。

**结构（13 章，通用骨架；章内"值"全部来自项目素材，禁止在 skill 中写死任何项目数值）**：

| # | 章节 | 内容要点 |
|---|------|---------|
| 1 | **目标与最终成果**（开篇必写） | **一句话目标**（做什么）：如「把 <模型/版本> 部署到 <硬件机群>」或「对 <已部署集群> 做 <测试/压测>，确认 <稳定性/容量>」；**背景与动机**（为什么做）；**最终成果 / 验收标准**（成功 = 什么，可测量：服务起来 / 压测 X 次 0 崩溃 / 指标达标）；**范围与边界**（做什么、不做什么）；素材来源：plan.md 目标 + ops-log 验收结论 |
| 2 | 部署总览 | 模型/服务规格、为什么走这条技术路线（兼容性结论）、关键决策表、部署形态 |
| 3 | 前置条件 | 硬件/软件/网络/端口要求 |
| 4 | 流程总览 | 阶段划分表（阶段/名称/产出/时长） |
| 5 | 阶段0 环境确认与加固 | GPU/驱动/磁盘检查、依赖包锁定、PATH/CUDA_HOME、工具链、基础依赖 |
| 6 | 阶段1 模型获取 | 下载命令（后台守护）、完成校验（文件数/大小） |
| 7 | 阶段2 **推理框架安装（核心）** | 兼容性核对（官方 vs 硬件）→ fork/补丁**从哪来/为什么/怎么用**→ 安装与验证命令（见 vLLM 通用要点） |
| 8 | 阶段3 推理验证 | 完整启动命令、每参数说明、启动成功判据、curl 中文验收 |
| 9 | 阶段4 服务化 | unit/容器定义全文、关键字段说明、自启 + reboot 验收 |
| 10 | **版本固化与验收基线** | **版本/指纹快照表（见「版本固化」节）** + 配置快照 + 压测/实测数据（KV/并发/时延/通过率） |
| 11 | 日常运维速查 | 看日志/重启/健康检查/改前备份/清 GPU 残留 |
| 12 | **坑点全录（pitfall，放最后）** | 按阶段分类（环境/安装/启动/稳定性/运维），每坑：症状→根因→解法 |
| 13 | 参考链接 + 制品/依赖清单 | fork/PR/Issue/官方文档链接；wheel/依赖存档位置 |

> 章 1（目标与最终成果）**开篇必写**——明确部署目标、预期成果与验收标准；章 9、11 为「稳定模板」章节；章 7、8、10 是**版本相关核心**，必须按 vLLM 通用要点 + 版本固化节落实。已实现实例的产物手册按同模板生成，见各项目 `docs/man/`。

### 模式 B：使用手册（`-usage`）

**目标读者**：最终用户——不关心内部怎么部署，只需要「能不能用、怎么用」。内容限定在能力、使用方式与限制（不涉及部署/内部实现）。
**结构（8 节）**：

| # | 章节 | 内容要点 |
|---|------|---------|
| 1 | 服务速览 | 一句话能力说明 + **真实** API 端点（取自部署）+ **真实**模型名 |
| 2 | 快速开始 | **仅一个 curl 示例**（代表性：含该模型特色参数，如 `thinking`/`reasoning_effort`），可直接跑；**不写 Python/多语言/多场景示例**——参数细节交给「请求参数说明」表 |
| 3 | 请求参数说明 | model / thinking / reasoning_effort / max_tokens / temperature（表格式，覆盖快速开始示例中的全部参数） |
| 4 | 输出字段解读 | content vs reasoning；content=null 的原因与解决（加大 max_tokens） |
| 5 | 典型场景示例 | 普通问答 / 深度思考 / 长上下文（不同参数组合的 curl，真实端点） |
| 6 | 使用限制与性能预期 | 上下文上限、并发、时延实测（来自 ops-log/raw-log 真实数据） |
| 7 | 常见问题 FAQ | 回答慢 / 内容在 reasoning / 报错 / token 不够等 |
| 8 | 联系与支持 | 真实负责人/渠道（由素材提供）；认证信息一律 `<需向管理员申请>` |

> usage 手册**独立自足**：不得依赖/引用**同仓库其他文档**（如 deploy 手册、生成器说明）——读者仅凭本手册即可使用，避免反向追问不相关文档；允许**外部链接**（官方文档/API 说明）作参考，而非"详见本仓库另一文档"式依赖。不涉及部署/内部实现/坑点内容；**IP/用户/端点等连接信息必须真实**；密码/密钥绝不出现。

## 原则

- 参数不全 → 只展示/提示，不生成；
- 名称不唯一 → 列候选让用户选，不猜；
- 已存在 → 先检测更新再问，无更新直接展示；
- 坑点永远放手册最后（deploy），usage 完全不出现；
- **可移植**：skill 不硬编码任何项目专属事实（模型名/版本号/机器/路径/数值），具体数值只出现在生成产物里；
