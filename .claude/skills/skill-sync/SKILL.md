# skill-sync — 跨项目技能同步

`dev-cookbook` 是通用技能的**聚合库**，各项目 `.claude/skills/` 是它的本地化副本。本 skill 负责两侧的双向同步：

- **pull（拉取）**：库 → 本地。补齐本地缺失的新内容，并对新内容做本地化适配；本地已有内容和本地化**原样保留**。
- **push（推送）**：本地 → 库。把本地项目中提炼出的新功能/新思路**通用化**后合并回库，并执行库的 `/checkpoint -y` 让变更落库落远端。

同步不是机械复制：pull 侧重本地化，push 侧重通用化；无实质差异时**直接跳过**，不为执行而执行。

## 参数

| 命令 | 作用 |
|------|------|
| `/skill-sync pull <技能名>` | 从技能库拉取指定技能到当前项目（本地化合并） |
| `/skill-sync push <技能名>` | 把当前项目的技能更新提炼回技能库（通用化 + checkpoint） |
| `/skill-sync list [关键词]` | 只读列出两侧同功能技能的对照与差异概要，不做修改 |

一次只处理一个技能；多个技能分次执行。

## 基本约定

### 技能库定位（确保零本地化）

按顺序尝试，命中即止：

1. 当前项目 `CLAUDE.md` 中的「技能同步配置」声明：

   ```markdown
   ## 技能同步配置
   - dev-cookbook: <绝对路径>
   ```

2. 与当前项目同级的 `dev-cookbook` 目录（在父目录下查找）
3. 询问用户输入路径

**校验**：目标必须包含 `ai-agent/claudecode/skills/` 目录，否则报错停止。

定位结果全程复用。跨平台约定：命令统一用 `git -C` + 带引号路径，文件读写用 Read/Glob/Grep 工具，不依赖 bash 专有语法。

### 同步范围

- 同步对象是整个技能目录：`SKILL.md` + `scripts/`、`references/` 等附件
- **不做**：删除技能、重命名技能、批量同步、引入额外同步状态文件
- 本 skill 自身是例外：`skill-sync` 设计为零本地化，若本地副本与库不一致，**以库为准直接覆盖本地**

### 同功能判定

名称只是线索，**实际处理的工作一致才是前提**。操作前必须：

1. 读两侧 `SKILL.md` 的 description 与正文主线流程
2. 名称相同但功能不同 → 拒绝同步并说明差异
3. 名称不同但功能相同（本地曾改名）→ 列出候选，让用户确认映射
4. 单侧缺失（库无 / 本地无）→ 建议改用反方向操作

### 新鲜度校验（时间只作警示，内容才是依据）

两侧时间来源：

```bash
git -C <repo> log -1 --format=%ci -- <技能目录>
```

未提交或非 git 项目回退到目录内文件最大 mtime，并标注「未提交」。展示给用户，例如：

```
库:   2026-09-18 09:20
本地: 2026-09-15 14:03
```

规则：

- **push 且本地明显偏旧**（超过 1 天）→ 先做内容 diff：
  - 库已包含本地演进 → 提示「库已最新」并跳过
  - 两边各有独特内容 → **以库为基底融合**，绝不覆盖
  - 仅本地有独特内容 → 正常 push
- **pull 且本地明显偏新** → 默认提示「本地已领先」并跳过；用户明确要求时才以本地为基底，仅融合库中缺失内容，绝不回退本地
- 同日微差 → 直接进入内容对比

### 前置检查

1. **技能库副本新鲜度**（避免在旧基底上操作、避免覆盖他人推送）：

   ```bash
   git -C <技能库路径> fetch
   git -C <技能库路径> status -sb
   ```

   落后且工作区干净 → `git -C <技能库路径> pull --ff-only`；落后但工作区脏或已分叉 → 提示用户处理后再继续。
2. **本地项目工作区状态**：有未提交变更时提示（pull 会产生新变更，建议先 `/checkpoint`），但不强制阻断。

## pull 流程（库 → 本地）

1. **定位 + 同功能判定**（见上）
2. **对比两侧**：

   ```bash
   git diff --no-index --stat <库技能目录> <本地技能目录>
   git diff --no-index --ignore-cr-at-eol <库技能目录> <本地技能目录>
   ```

   忽略纯行尾（CRLF/LF）差异；先判断是否**无实质差异**——若是，输出摘要后直接跳过。
3. **识别三类内容**：
   - 仅库有 → 本地缺失的新功能/新流程/新附件
   - 仅本地有 → 本地已有内容与本地化，保留
   - 两侧都有但不同 → 可能是本地化改写，也可能是双方都改过
4. **合并规则**：
   - 仅库有的内容：添加，并按第 5 步本地化
   - 仅本地有的内容：原样保留
   - 同一区块双改（非纯本地化）：**一次性汇总所有冲突点**，给出选项（取库 / 取本地 / 融合 / 暂缓），由用户决定
   - description：库通用基底 + 本地增量；frontmatter `name` 跟随本地目录名
   - 附件脚本同样处理；`.ps1` 首行保持 `#Requires -Version 7`
5. **本地化适配**（参照当前项目 `CLAUDE.md` 与本地 skill 中已有的本地化写法）：
   - 项目路径、目录约定、输出目录
   - MCP 工具名与 server 名（由通用描述替换为本地实际配置）
   - 分支命名、提交说明格式
   - 术语、章节名
   - 引用检查：新内容引用了本地不存在的技能/MCP/工具 → 提示先同步依赖，或做本地化降级
6. **验证**：展示最终 diff 摘要，校验 frontmatter 合法
7. **收尾**：提示本地项目可运行 `/checkpoint`（不强制）；若本地 `CLAUDE.md` 有技能清单/配置惯例，询问是否需要登记

## push 流程（本地 → 库）

1. **定位 + 同功能判定**
2. **对比 + 新鲜度校验**（见上）
3. **识别本地演进**：相对库版本的新功能、新流程、新思路、附件变化
   - 库已包含这些演进 → 提示「无需推送」并跳过
   - 仅本地有独特内容，或两边各有独特内容 → 进入合并
4. **通用化提炼**（以库当前版本为基底，禁止整段覆盖）：
   - 项目路径 / 用户名 / 机器名 / 项目特有术语 → 通用表述，或改为「项目 CLAUDE.md 可声明」的可配置项
   - 具体 MCP 工具名 → 通用能力描述（如「当前环境可用的 Web 搜索工具」），保留工具类型说明
   - 项目特有输出目录 / 分支约定 → 通用约定或可配置
   - 保持库既有的通用化风格；发现库中残留他项目的专有内容，一并提示修正
5. **附件同步**：脚本/参考文件一并通用化；新增技能或 description 变化时，更新 `ai-agent/claudecode/skills/README.md` 索引表
6. **验证**：diff 摘要 + frontmatter 校验 + 索引完整性
7. **执行技能库 `/checkpoint -y`**：
   - 读取 `<技能库>/.claude/skills/checkpoint/SKILL.md`，按其流程在技能库中执行（`-y` 语义：跳过确认）
   - **只提交本次同步相关文件**；若技能库存在无关未提交变更，先报告，不夹带
   - 提交说明按 checkpoint 格式，如 `ai-agent/claudecode/skills/<name>: <改动>`
   - push 被拒 → 如实报告，不强行
8. **收尾**：输出同步报告（改了什么、commit、是否已推远端）

## list 模式

只读展示，不修改任何文件：

| 技能 | 本地名 | 库更新时间 | 本地更新时间 | 差异概要 | 建议 |
|------|--------|------------|--------------|----------|------|

建议方向：无差异 → 已同步；库新 → pull；本地新 → push；两边都有独特内容 → 需人工确认。

## 禁止事项

- 不做机械复制与整目录覆盖
- 不做无意义同步（无实质差异必须跳过）
- 不自动删除 / 重命名 / 批量同步
- 不修改两个仓库之外的任何文件
- 冲突不硬合：用户不确认，不覆盖任何一侧内容
